# Hook dispatching

This document explains the request-time half of the hook system: the `Dispatcher` interface, what `DefaultDispatcher` does in each of its four methods, how rate limits and audit events are attached to a dispatch, how `WithLifecycle` wraps a flow, and where each firing site calls the dispatcher.

---

## `Dispatcher`

```go
type Dispatcher interface {
	RunBefore(hctx *HookContext, point HookPoint, payload behemoth.M) (behemoth.M, error)
	RunAfter(hctx *HookContext, point HookPoint, result any) error
	RunAfterTx(hctx *HookContext, point HookPoint, result any) error
	Fail(hctx *HookContext, point HookPoint, reason FailureReason) error
}
```

It is defined in `core/plugins.go` and reached through `AuthContext.Dispatcher`. Firing sites depend on the interface: the managers take it as a constructor parameter, plugins read it from the `AuthContext`, and tests replace it with small fakes (`passDispatcher`, `recordingDispatcher`).

There are three phases and four methods. The after phase has two, because an after chain is run under two different contracts:

| Method | Phase | Used for | A handler error |
| --- | --- | --- | --- |
| `RunBefore` | before | both tiers | stops the chain and is returned |
| `RunAfter` | after | Tier 2 points and the committed data points | is logged; the chain continues |
| `RunAfterTx` | after | the in-transaction data points | stops the chain and is returned |
| `Fail` | failed | Tier 2 points | is logged; the chain continues |

`RunAfter` and `RunAfterTx` run the same kind of chain with the same handler type. The firing site chooses the contract by choosing the method. A point is not marked as one or the other in the catalog, so a point should be fired with one of the two methods throughout.

## `DefaultDispatcher`

```go
type DefaultDispatcher struct {
	catalog      core.HookCatalog
	frozenChains map[core.HookPoint][]registeredHandler
	rateLimiter  core.RateLimiter
	tel          *telemetry.Telemetry
}
```

`Boot` builds one and puts it on the `AuthContext`. It holds no per-request state. After `Boot` the catalog and the chains are only read, so the dispatcher is safe to call from any number of goroutines.

### The common first step: `checkPhase`

Every method starts with:

```go
func (d *DefaultDispatcher) checkPhase(op string, point core.HookPoint, expected core.HookPhase) (core.HookPointDef, error)
```

It looks the point up in the catalog and compares the declared phase with the phase the method dispatches.

| Outcome | Result |
| --- | --- |
| the point is not declared | `ConfigurationError`: `point "x" was never declared` |
| the point is declared with another phase | `ConfigurationError`: `point "x" is phase "after", cannot dispatch as "before"` |
| otherwise | the `HookPointDef`, which `RunAfter` and `Fail` need for the audit spec |

The second step, also common to all four, is `forPoint`: the handlers, the rate limiter and the audit recorder get a shallow copy of the firing site's context with `Point` and `Phase` set. The copy shares the site's `Values` map. See [3. Hook Context](<3. Hook Context.md>).

On an error from `checkPhase` no handler runs. The error describes a mistake in the firing code, not in a handler, and it is the same kind of error `Prepare` and `Boot` return for setup mistakes. For `RunAfter` and `Fail` it is the only error they ever return.

`Fail` has one step before it: an empty point name returns nil at once.

### `RunBefore`

`RunBefore` runs these steps:

1. `checkPhase(point, before)`.
2. If a rate limiter is set, `rateLimiter.CheckHookLimit(hctx.Ctx, point, hctx)`. An error is returned at once and no handler runs.
3. The current payload is the input, or an empty map when the input is nil.
4. For each handler in `frozenChains[point]`, in order:
   - assert the handler to `BeforeHookFunc`
   - call it with the current payload, inside `safeInvokeBefore`, which recovers a panic
   - on an error, return `nil, err`
   - a non-nil returned map becomes the current payload; a nil one leaves it as it is
5. Return the current payload.

With no handlers the input payload is returned unchanged, or an empty map for a nil input. The payload returned with a nil error is never nil. The reasons are in [3. Hook Context](<3. Hook Context.md>).

The error of a handler is returned as it is, not wrapped. The caller sees the handler's `errs` type and the HTTP layer can map it. A rate-limit rejection comes back the same way, as a `CategoryRateLimited` error, so the caller treats it like a handler's veto.

### `RunAfter`

`RunAfter` runs these steps:

1. `checkPhase(point, after)`. An error is returned.
2. For each handler: assert to `AfterHookFunc` and call it inside `safeInvokeAfter`. An error is logged (`after-hook failed`, with the point and the owner) and the loop continues.
3. `recordAudit`.
4. Return nil.

Every handler runs, whatever the earlier ones did. A welcome-email handler that fails does not keep an analytics handler from running, and neither changes the result of the flow.

### `RunAfterTx`

`RunAfterTx` runs these steps:

1. `checkPhase(point, after)`.
2. For each handler: assert to `AfterHookFunc` and call it inside `safeInvokeAfter`. An error is returned at once.
3. `recordAuditTx`. An error is returned.
4. Return nil.

It is `RunBefore` without a payload and without the rate limit. The store bridge calls it and returns the error to the store, which rolls the transaction back.

The audit step differs from `RunAfter`'s. The write can still be rolled back, by a later write in the caller's transaction, so the event is written through that transaction (`HookContext.Tx`) and shares its fate. See [Audit at an after or failed point](#audit-at-an-after-or-failed-point).

### `Fail`

`Fail` runs these steps:

1. Return nil if `point == ""`.
2. `checkPhase(point, failed)`. An error is returned.
3. For each handler: assert to `FailedHookFunc` and call it inside `safeInvokeFailed`. An error is logged (`failed-hook handler errored`) and the loop continues.
4. `recordAudit` with the reason.
5. Return nil.

### The four side by side

| | `RunBefore` | `RunAfter` | `RunAfterTx` | `Fail` |
| --- | --- | --- | --- | --- |
| Empty point | configuration error | configuration error | configuration error | nil, nothing runs |
| Undeclared or wrong phase | configuration error | configuration error | configuration error | configuration error |
| Rate limit | checked first | no | no | no |
| Handler gets | the payload so far | the result | the result | the reason |
| Handler returns an error | chain stops, error returned | logged, chain continues | chain stops, error returned | logged, chain continues |
| Handler panics | chain stops, internal error returned | logged, chain continues | chain stops, internal error returned | logged, chain continues |
| Audit event | no | if declared, best effort | if declared, in the transaction | if declared, best effort |
| Returns | the final payload, or the first error | nil | the first error, or nil | nil |

### Panics

Each handler call goes through a `safeInvoke...` helper with a deferred `recover`. A panic becomes an `InternalError` whose message names the owner and the point:

```
panic in "totp"'s handler on "auth.signIn.credentialsVerified": <value>
```

From there it is handled like an error the handler returned: fatal to the chain in `RunBefore` and `RunAfterTx`, logged in `RunAfter` and `Fail`. A panicking handler does not take the process down, and inside a data hook it rolls the write back like any other error.

`safeInvokeAfter` and `safeInvokeFailed` only recover; the method that called them logs or returns the error. `safeInvokeBefore` also logs the panic itself (`before-hook panicked`) before `RunBefore` returns it.

### The type assertion

Handlers are stored as `any` and asserted to the phase's function type on each call. The registry only stores a `BeforeHookFunc` under a before point, and so on, so a failed assertion would mean a bug in the registry. The dispatcher still handles it: `RunBefore` and `RunAfterTx` return an internal error, `RunAfter` and `Fail` log it and go on to the next handler.

### Logging

Handler errors go to `Telemetry.Logger.Error` with the fields `point`, `plugin` (the owner) and `error`. `Boot` replaces a nil `BootConfig.Telemetry` with no-op implementations, so with the defaults a failing after handler leaves no trace. An application that relies on after hooks should configure a logger.

## Rate limits at a before point

A `HookRateLimitRule` attaches a limit to a before point. It is declared through `PluginInitContext.RateLimits` during `Declare`, and the rate-limit catalog rejects a rule whose point is undeclared or not a before point.

At dispatch, step 2 of `RunBefore` calls `DefaultRateLimiter.CheckHookLimit`:

```go
rules := rl.catalog.RulesForHook(point)
for _, rule := range rules {
	ruleKey, ok := rule.KeyFunc(hctx)
	if !ok {
		continue // the rule does not apply to this call
	}
	key := rule.Name + ":" + ruleKey
	if err := rl.evaluate(ctx, rule.Name, key, "", limiter, rule.Limit, rule.Action, rule.LockoutFor); err != nil {
		return err
	}
}
```

- Every rule of the point is evaluated and all have to pass. Route rules work differently: there the single most specific rule applies. Two plugins can each have their own reason to bound one point, and both limits should hold.
- The key comes from the `HookContext`, not from the payload. A rule can count per client address (`core.KeyByClientIP`, from the caller, which has none for code in the process), or per value the firing site published in `hctx.Values` before the dispatch: the email of a sign-up or sign-in, the user of a session create, the kind and subject of a token issue. [`../ratelimit/rate_limiter.md`](../ratelimit/rate_limiter.md) lists them under *What a hook rule can key on*.
- `KeyFunc` also returns whether the rule applies. A rule that has nothing to count the call per (no request, no email) is skipped, and the others are still checked.
- The check runs before the handlers. A rejected call does not reach any of them.
- The counter is incremented through a store that is never bound to a transaction. An attempt that is later rolled back still counts.

Because the check is inside `RunBefore`, it applies to every before point of both tiers with no code at the firing site. Core declares no hook rules today. The limiter itself is described in [`../ratelimit/rate_limiter.md`](../ratelimit/rate_limiter.md).

## Audit at an after or failed point

A point declared with `Audit: &core.AuditSpec{}` gets one audit event recorded by the dispatcher each time it fires, after the handlers. `DefaultDispatcher.auditEvent` builds it; which method fired the point decides how it is written.

| Dispatched with | Written | A failed write |
| --- | --- | --- |
| `RunAfter`, `Fail` | `recordAudit`: through `Telemetry.RecordAudit`, once the operation is over | is logged at Error; the dispatch is unaffected |
| `RunAfterTx` | `recordAuditTx`: through the write's transaction for a recorder that supports it, after the commit for any other | is returned, and the store rolls the write back |

| Event field | Value |
| --- | --- |
| `Type` | `AuditSpec.Type`, or the point name when that is empty |
| `Outcome` | `failure` for `Fail`, `success` otherwise |
| `SubjectType`, `SubjectID` | the failure reason's subject; else the result's (a `behemoth.Model`, or a `core.AuditSubject`); else `Values[HookValueUserID]` |
| `ActorID`, `ActorType`, `DelegateID`, `DelegateType` | the caller's principal and delegate (`telemetry.AuditActor`); else, for a success of an anonymous caller a transport authenticated, the subject's user; else anonymous for such a caller, and system for code that did not name itself |
| `Metadata` | for `Fail`: `FailureReason.Metadata`, `code`, and `cause` when the reason has one. For a token: `kind`. |
| `SessionID`, `IPAddress`, `UserAgent`, `RequestID` | the caller's session and peer, and the context's request ID. `BootConfig.Audit.OmitIPAndAgent` leaves the address and the user agent out. |

Core declares a spec on the after and failed points of sign-up, sign-in, sign-out, sessions, and tokens, and on `data.user.afterCreate` and `data.user.afterUpdate`. Before points never record.

The event model, the derivation rules and the storage are described in [`../telemetry/audit.md`](../telemetry/audit.md).

--- | --- |
| `Type` | `AuditSpec.Type`, or the point name when that is empty |
| `ActorID` | an empty string today (`actorFrom` is a stub) |
| `SubjectID` | the primary key of the result when it is a `behemoth.Model`, otherwise nil. Always nil for `Fail`. |
| `Metadata` | for `Fail`: `code`, and `cause` when the reason has one |
| `Timestamp` | now |

A failure to record is logged as a warning and does not affect the dispatch.

`auth.signIn.failed` is the only point core declares with an `AuditSpec`. Each rejected sign-in records an event of type `auth.signIn.failed` with the reason code.

Before points and `RunAfterTx` never record. The committed data points are dispatched with `RunAfter` and can be audited; core declares no spec on them.

## Firing a point

A firing site does four things: opens its operation, builds a `HookContext`, calls the method that matches the point's phase, and handles the returned error.

```go
// one operation per call: both points share Values, nested under the caller's
ctx = core.BeginOperation(ctx)
hctx := &core.HookContext{Ctx: ctx, Auth: ac, Values: core.HookValuesFrom(ctx)}

// before: the error is a veto, a rate limit, or a configuration error
payload, err := disp.RunBefore(hctx, HookInviteBeforeAccept, payload)
if err != nil {
	return err
}

// ... the operation ...

// after: the error can only be a configuration error
if err := disp.RunAfter(hctx, HookInviteAccepted, invite); err != nil {
	return err
}
```

Where to place the calls relative to a transaction decides the tier. A flow that fires its after point inside `Store.Transaction` announces something that can still be rolled back. Core's Tier 2 sites all fire after the write has returned.

### `WithLifecycle`

Most flows have the same shape: a before point, the work, an after point, and a failed point when a before handler says no. `core.WithLifecycle` wraps a function with that shape:

```go
func WithLifecycle[TIn, TOut any](
	dispatcher Dispatcher,
	before, success, failed HookPoint,
	fn func(hctx *HookContext, in TIn) (TOut, error),
) func(hctx *HookContext, in TIn) (TOut, error)
```

The returned function does this:

| Step | Action | On error |
| --- | --- | --- |
| 0 | `AsOperation(hctx)`: the flow becomes one operation | |
| 1 | convert `in` to a payload (`structToM`) | return the error |
| 2 | `RunBefore(before, payload)` | `FailIfRejected`: for a rejection, `Fail(failed, {Code: FailureRejectedByHook, Cause: err})`; then return the before error |
| 3 | convert the returned payload back into `in` (`mFromStruct`) | return the error |
| 4 | `fn(hctx, in)` | return the error; no `Fail`, no after chain |
| 5 | `RunAfter(success, out)` | return the configuration error |
| 6 | return `out` | |

Details:

- **The before chain can rewrite the input.** `fn` receives what the handlers returned, not what the caller passed.
- **`fn` fires its own failed point.** `WithLifecycle` can't tell a business rejection from an infrastructure error in `fn`'s return value, so it fires nothing in step 4. The body calls `dispatcher.Fail` itself at each business rejection, with a specific code.
- **Only a rejection fires the failed point in step 2.** `core.FailIfRejected` asks `errs.IsRejection`. A handler's untyped error, a panic (an internal error) or a database error inside a handler is returned without a `Fail` call.
- **A rate-limit rejection counts as a hook rejection.** It comes out of `RunBefore` like a veto and its category is a rejection, so step 2 fires the failed point with `rejected_by_hook`.
- **Every site that runs a hook chain inside a flow uses `FailIfRejected`.** The flow bodies call it for `auth.signIn.credentialsVerified` and for a write whose data hooks may refuse it, so the code and the rule are the same everywhere. The caller passes the subject and metadata; the helper sets `Code` and `Cause`.
- **A configuration error from `Fail` replaces the original error** in step 2. The same holds in the flow bodies.
- **`failed` may be empty.** `Fail` returns nil for an empty point, so a flow without a failed point passes `""`.
- **One operation for all steps.** Step 0 makes a copy of the context whose `Ctx` carries its `Values`. That copy is used for every dispatch and handed to `fn`, so the flow's points share `Values`, and the store writes and manager calls `fn` makes with `hctx.Ctx` start from a copy of them. See [3. Hook Context](<3. Hook Context.md>).

The email/password plugin builds its two wrapped flows once, in `Init`:

```go
p.signUp = core.WithLifecycle(ac.Dispatcher, hooks.HookSignUpBefore, hooks.HookSignUpAfter, hooks.HookSignUpFailed, p.signUpBody)
p.signIn = core.WithLifecycle(ac.Dispatcher, hooks.HookSignInBefore, hooks.HookSignInAfter, hooks.HookSignInFailed, p.signInBody)
```

The wrapped functions are private. The plugin's exported `SignUp(ctx, input)` and `SignIn(ctx, creds)` build the flow's `HookContext` from a `context.Context` and call them, and the route handlers go through those two methods as well.

`WithLifecycle` is a helper, not a requirement. `SignOut`, the managers and `dataHooks` call the dispatcher directly, and so does `signInBody` for its checkpoint in the middle of the flow.

### The firing sites in core

**Sign-in** (`plugins/emailpassword`), the fullest example:

| Order | Dispatch | Fired by |
| --- | --- | --- |
| 1 | `RunBefore(auth.signIn.before)` | `WithLifecycle` |
| 2 | `Fail(auth.signIn.failed)` with `user_not_found`, `no_credential_account` or `invalid_credentials` | `signInBody`, on the matching rejection; the flow ends |
| 3 | `RunBefore(auth.signIn.credentialsVerified)` | `signInBody`, once the password matched |
| 4 | `Fail(auth.signIn.failed)` with `rejected_by_hook` | `signInBody` through `FailIfRejected`, when step 3 returned a rejection; the flow ends. Any other error ends the flow without a `Fail` |
| 5 | `RunBefore(auth.session.beforeCreate)` | `SessionManager.Create` |
| 6 | `RunAfter(auth.session.afterCreate)` | `SessionManager.Create` |
| 7 | `RunAfter(auth.signIn.after)` | `WithLifecycle` |

A handler on `auth.signIn.credentialsVerified` has two ways to act. Returning an error ends the sign-in. Setting `requireStepUp: true` in the payload lets it continue with a pending session, which is how a second-factor plugin asks for its step without the email/password plugin knowing about it.

**Sign-up:** `RunBefore(auth.signUp.before)`, then the store's data points inside the transaction (see [6. Data Hooks](<6. Data Hooks.md>)), then `RunAfter(auth.signUp.after)`. `signUpBody` fires `auth.signUp.failed` with `user_exists`.

A data hook's veto reaches `signUpBody` as the error of its store transaction. What `signUpBody` does with that error depends on its type:

| The transaction's error | Returned to the caller | `auth.signUp.failed` |
| --- | --- | --- |
| a `DomainError` that is a rejection: category validation, conflict, unauthorized, forbidden or rate limited. The store's conflict for a value of a unique column another user holds is one (`username_taken`) | as it is | fired with `rejected_by_hook` and the error as `Cause` |
| the duplicate key of `email`: another sign-up took the address after the lookup | `email_taken` | fired with `user_exists` |
| any other `DomainError` (database, transaction, duplicate key, internal, ...) | as it is | not fired |
| an untyped error | as it is; the router answers `500` without its text and logs it | not fired |

`errs.IsRejection` draws the first line, from the error's category (`Category.IsRejection` in `errs/errors.go` holds the list). It keeps an outage from being counted as a refused sign-up, the same rule `signInBody` follows. A handler that vetoes with an untyped error is not recognized as a veto, so a data hook handler should return a `errs` type, as the `BeforeHookFunc` contract asks.

`handleSignUp` returns every error to the router, whose `ErrorMapper` picks the status and sends the error's public message. The flow's own rejections are typed as well (`email_invalid_input`, `password_invalid_input`, `email_taken`); see [`../plugins/emailpassword.md`](../plugins/emailpassword.md).

**Sign-out** (`SignOut`): `AsOperation`, then `RunBefore(auth.signOut.before)`, `SessionManager.Revoke`, `RunAfter(auth.signOut.after, nil)`.

**Session manager** (`auth/session.go`):

| Method | Before | Work | After |
| --- | --- | --- | --- |
| `Create` | `auth.session.beforeCreate` | `Store.CreateSession`, cache set | `auth.session.afterCreate` |
| `revokeModel` | `auth.session.beforeRevoke` | `Store.UpdateSessionAt`, retried when another update wins, then the revoked copy to the cache | `auth.session.afterRevoke` |
| `Discard` | none | cache delete; the rows were deleted with their user | `auth.session.afterRevoke`, for each session that was live |

Both methods open their operation with `core.BeginOperation(ctx)` before the first dispatch. Every revoke path goes through `revokeModel`, including eviction of the oldest session and revoke-all, so the points fire for each session revoked. A session that is already revoked returns early and fires nothing.

**Token manager** (`auth/token.go`):

| Method | Dispatches |
| --- | --- |
| `Issue` | `RunBefore(token.beforeIssue)`, persist, `RunAfter(token.afterIssue)` |
| `Consume` | on success `RunAfter(token.consumed)`; on a rejected consume `Fail(token.failed)` with the classified code |
| `Verify`, `Revoke` | none |

`Consume` fires after its transaction has returned, for both outcomes. `Issue` and `Consume` open their operation with `core.BeginOperation(ctx)`.

**Store bridge** (`dispatch/datahooks.go`): described in [6. Data Hooks](<6. Data Hooks.md>).

## Limits to know

These limits apply:

- **An undeclared point is found at request time.** `checkPhase` runs when the point is fired. For an after or failed point the work is already done by then: the session exists, and the caller gets an error. Core's points are covered by a test. A plugin firing its own points has no such check. The options are discussed in [`../../ongoing.md`](../../ongoing.md).
- **After handlers run inline.** `RunAfter` calls each handler in the calling goroutine and returns when the last one has. A slow handler delays the response.
- **No timeout per handler.** A handler is bounded only by `hctx.Ctx`, and only if it honours it.
- **No retry.** A failed after handler is logged once.
- **Handler errors in `RunAfter` and `Fail` are invisible to the caller.** That is the contract, and it means tests have to assert on the handler's effect or on the logger.
- **A catalog lookup per dispatch.** `checkPhase` takes the catalog's read lock and reads a map on every call. The cost is small next to the database write or password hash a hook surrounds.

## Design decisions

### Firing sites call the dispatcher themselves, with a wrapper for the common shape

**Context:** Hook points have to be fired somewhere around each flow. The question is whether the flow's author does it or the framework does.

**Options considered:**

- *Every flow dispatches by hand.* Full control over where each point fires. Easy to forget a point or to fire the failed point on the wrong errors.
- *The framework wraps every route with before and after dispatches.* Nothing to forget. A flow can't fire a point in the middle (`credentialsVerified`), can't choose which errors count as rejections, and code that runs outside a route gets no hooks.
- *Both: a generic wrapper for the before, after, and veto shape, and the dispatcher on the `AuthContext` for everything else.*

**Decision:** Both. `WithLifecycle` covers the outer shape of sign-up and sign-in, and the bodies call `Fail` and `RunBefore` directly where the flow needs it. The wrapper works on a function, not a route, so the wrapped flow fires its points when called from anywhere.

### One helper reports a hook chain's error

**Context:** A flow that runs a before chain, or a write with data hooks, gets back one error. It has to decide whether that is a refusal, which fires the failed point, and how to name it. Each site decided for itself: `WithLifecycle` fired for every error, the sign-in flows fired for every error and named it `secondFactorRejected`, and two plugins had a private `isRejection`.

**Options considered:**

- *A constant for the code and an exported `IsRejection`, used by each site.* Small. Every new site still has to remember both.
- *A field on `DomainError` that says business or system.* The handler states it outright. It is a second source next to the category, and the two can disagree.
- *The dispatcher decides inside `RunBefore`.* Nothing to remember. `RunBefore` does not know the flow's failed point or the subject, and a data hook's error comes out of a store write, not out of `RunBefore`.
- *A function in `core` that takes the error, the failed point and the site's subject and metadata.*

**Decision:** The function, `core.FailIfRejected`. The category decides what a rejection is (`errs.Category.IsRejection`), and the code is always `core.FailureRejectedByHook`, since the site can't know which handler refused. The reason is the cause. `Dispatcher` stays as it is, so an application's own dispatcher needs no change. The full record, with the audit metadata and the casing of codes, is [ADR-0001](../decisions/0001-reporting-a-hook-refusal.md).

### A handler error in `RunAfter` is logged, not returned

**Context:** A Tier 2 after point fires when the operation has succeeded and its writes are committed.

**Options considered:**

- *Return the first error.* The caller learns about it. The caller can't undo the operation, so a failed welcome email would turn a successful sign-up into an error response, and later handlers would be skipped.
- *Log and continue.* The operation's result stands, and each handler gets its turn. A failure is only visible in the log.

**Decision:** Log and continue. Work that should be able to fail the operation belongs in a before point, or in the in-transaction data points, which use `RunAfterTx`.

### An undeclared point is a configuration error
Recorded in [`../models/models.md`](../models/models.md#data-hooks-and-transactions) under "An undeclared hook point is a configuration error, not a panic".
