# Hook taxonomy

This document explains how hook points are classified: the three phases, the two tiers, and the branches inside each tier. It then lists every point core declares, who fires it and how.

---

## Phases

A phase says what a handler on the point may do. It is a field of the declaration (`HookPointDef.Phase`), and a point has one.

| Phase | Constant | Handler type | A handler can |
| --- | --- | --- | --- |
| before | `BeforeHookPhase` | `BeforeHookFunc` | rewrite the payload, or stop the operation by returning an error |
| after | `AfterHookPhase` | `AfterHookFunc` | react to the result. Whether its error matters depends on the tier. |
| failed | `FailedHookPhase` | `FailedHookFunc` | react to a business rejection. Its error is logged. |

The phase is checked at three places, so a mismatch can't reach a handler:

| Where | Check | Failure |
| --- | --- | --- |
| `DefaultHookCatalog.Declare` | the phase is one of the three | `Prepare` fails |
| `DefaultHookRegistry.register` | `OnBefore` on a before point, `OnAfter` on an after point, `OnFailed` on a failed point | `Boot` fails |
| `DefaultDispatcher.checkPhase` | `RunBefore` on a before point, `RunAfter` and `RunAfterTx` on an after point, `Fail` on a failed point | the dispatch returns a configuration error |

An operation with several sides is several points. Session creation is `auth.session.beforeCreate` and `auth.session.afterCreate`. Sign-up is three points.

The phase is not always the position in the flow. `auth.signIn.credentialsVerified` is a before point that fires in the middle of sign-in, after the password check. "Before" means the handler gets a payload and can stop what follows.

## Tiers

The tier says who fires the point and around what. It is not a field anywhere in the code. It follows from the firing site and from the dispatcher method that site calls.

| | Tier 1: data points | Tier 2: flow points |
| --- | --- | --- |
| Fired by | the store, through `dataHooks` | a plugin flow or a manager, calling the dispatcher itself |
| Around | one write to one table | a whole operation (a sign-in, a token consume) |
| Knows | the row | the intent |
| Database transaction | inside the write's transaction | outside any store transaction |
| `HookContext.Tx` | the store bound to the transaction | nil |
| Fires when | any code path writes the table through the store | that one flow runs |
| Name prefix | `data.` | `auth.`, `token.` |

A plugin picks the tier by what it cares about. A plugin that adds a row for every new user wants Tier 1: users are created by email sign-up today and would be created by OAuth sign-up or an admin tool tomorrow, and `data.user.afterCreate` fires for all of them. A plugin that demands a second factor wants Tier 2: verifying a password writes nothing, so no data point fires there at all.

Both tiers fire independently during one request. The sign-up trace in [`hooks.md`](hooks.md#one-sign-up-end-to-end) shows them nested: the Tier 2 points wrap the flow, and the Tier 1 points fire inside it when the flow writes the user.

### The branches

Tier and phase together give six kinds of point. Each row is a different contract for the handler:

| Branch | Dispatched with | Handler error | Later handlers | Rate limit | Audit | Example |
| --- | --- | --- | --- | --- | --- | --- |
| Tier 1 before | `RunBefore` | aborts the write | don't run | checked | no | `data.user.beforeCreate` |
| Tier 1 after, in transaction | `RunAfterTx` | rolls the write back | don't run | no | if declared, in the transaction | `data.user.afterCreate` |
| Tier 1 after, committed | `RunAfter` | logged | run | no | if declared | `data.user.created` |
| Tier 2 before | `RunBefore` | stops the flow | don't run | checked | no | `auth.signIn.before` |
| Tier 2 after | `RunAfter` | logged | run | no | if declared | `auth.signIn.after` |
| Tier 2 failed | `Fail` | logged | run | no | if declared | `auth.signIn.failed` |

Things to read from the table:

- **The two before branches behave the same.** `RunBefore` does not know the tier. The difference is around it: a Tier 1 before handler runs with a transaction open and a `Tx` to write through.
- **Tier 1 has two after branches.** The in-transaction point is part of the write and can veto it. The committed point is a notification, and behaves like a Tier 2 after point. They are separate points (`data.user.afterCreate` and `data.user.created`), not one point fired twice.
- **Tier 1 has no failed branch.** A write that fails returns its error to the caller, and no point fires for it. `Dispatcher.Fail` returns nil for an empty point name so that generic code can pass "no failed point" without a branch.
- **The after-phase split is the dispatcher's, not the catalog's.** `data.user.afterCreate` and `auth.signIn.after` are both declared as `AfterHookPhase`. What makes one of them able to roll back is that `dataHooks` calls `RunAfterTx` for it and the store acts on the returned error. Nothing in the declaration says which method a point is dispatched with.

The last point has a consequence for anyone adding a firing site: the contract of an after point is decided by the method the site calls. `RunAfterTx` is meant for the store bridge. A flow that called it for a Tier 2 point would get the first handler error back, with no transaction to roll back.

### Session and token points are Tier 2

`auth.session.*` and `token.*` sit next to a table write, but the managers fire them, not the store:

- they fire around the operation (a revoke also ends the cache entry; a consume may happen in key-value storage with no table involved)
- they fire outside any store transaction, so `Tx` is nil
- their after handlers are dispatched with `RunAfter`, so an error is logged

`coreDataHookPoints` has no entry for `sessions` or `tokens` for this reason. An entry would fire the points a second time from the store and open a transaction around every session and token write.

## Names

Point names follow `<domain>.<resource or flow>.<moment>`:

| Part | Tier 1 | Tier 2 |
| --- | --- | --- |
| domain | `data` | `auth`, `token`, or a plugin's own |
| resource or flow | the table's model: `user` | `signUp`, `signIn`, `signOut`, `session` |
| moment | `beforeCreate`, `afterCreate`, `beforeUpdate`, `afterUpdate`, `beforeDelete`, `afterDelete`, `created`, `updated`, `deleted` | `before`, `after`, `failed`, or a named checkpoint |

The token points drop the middle part: `token.beforeIssue`, `token.consumed`.

The convention is not enforced. `DefaultHookCatalog.Declare` checks that the name is not empty and not already declared, and nothing about its shape. A plugin can declare `auth.something` as long as core has not. Core declares first, so its names are always taken by the time a plugin declares.

A name is a contract with every handler registered on it. Renaming a point breaks those registrations at `Boot` ("point was never declared"), which is loud, but it still breaks them. Add points, don't rename them.

## Points core declares

`CoreDeclareHookPoints` in `engine/init.go` declares these under owner `core`. `TestCoreDeclaresTheHookPointsItFires` pins the list and the phases.

### Tier 1

Fired by `dataHooks` for the `users` table.

| Point | Phase | Dispatched with | Fires |
| --- | --- | --- | --- |
| `data.user.beforeCreate` | before | `RunBefore` | before the insert, in the transaction |
| `data.user.afterCreate` | after | `RunAfterTx` | after the insert, before commit |
| `data.user.created` | after | `RunAfter` | after the outermost transaction committed |
| `data.user.beforeUpdate` | before | `RunBefore` | before the update, in the transaction |
| `data.user.afterUpdate` | after | `RunAfterTx` | after the update and read-back, before commit |
| `data.user.updated` | after | `RunAfter` | after the outermost transaction committed |
| `data.user.beforeDelete` | before | `RunBefore` | in the transaction, before any row is removed |
| `data.user.afterDelete` | after | `RunAfterTx` | after the user and the rows deleted with it are gone, before commit |
| `data.user.deleted` | after | `RunAfter` | after the outermost transaction committed, after the deleted sessions' `auth.session.afterRevoke` |

### Tier 2

| Point | Phase | Fired by | Fires |
| --- | --- | --- | --- |
| `auth.signUp.before` | before | `WithLifecycle` around `signUpBody` | before validation |
| `auth.signUp.after` | after | `WithLifecycle` | after `signUpBody` returned the user |
| `auth.signUp.failed` | failed | `WithLifecycle`, `signUpBody` | a before handler stopped the flow, or the email is taken |
| `auth.signIn.before` | before | `WithLifecycle` around `signInBody` | before the user lookup |
| `auth.signIn.credentialsVerified` | before | `signInBody` | after the password matched, before the session is created |
| `auth.signIn.after` | after | `WithLifecycle` | after `signInBody` returned |
| `auth.signIn.failed` | failed | `WithLifecycle`, `signInBody` | each business rejection |
| `auth.signOut.before` | before | `SignOut` | before the session is revoked |
| `auth.signOut.after` | after | `SignOut` | after the revoke; the result is nil |
| `auth.session.beforeCreate` | before | `DefaultSessionManager.Create` | before the session row is written |
| `auth.session.afterCreate` | after | `DefaultSessionManager.Create` | after the row is written and cached |
| `auth.session.beforeRevoke` | before | `DefaultSessionManager.revokeModel` | before the state changes |
| `auth.session.afterRevoke` | after | `DefaultSessionManager.revokeModel` | after the update and the cache delete |
| `auth.session.afterRevoke` | after | `DefaultSessionManager.Discard` | after a user delete committed, once per session that was live, with reason `user_deleted`. `beforeRevoke` does not fire for these |
| `token.beforeIssue` | before | `DefaultTokenManager.Issue` | before the token is stored |
| `token.afterIssue` | after | `DefaultTokenManager.Issue` | after the token is stored |
| `token.consumed` | after | `DefaultTokenManager.Consume` | after a successful consume |
| `token.failed` | failed | `DefaultTokenManager.Consume` | a consume was rejected |

The payload, result, and reason of each point are listed in [`../../api/hooks.md`](../../api/hooks.md#hook-point-reference).

Core declares the `auth.signUp.*`, `auth.signIn.*`, and `auth.signOut.*` points, but the email/password plugin fires them. Without that plugin they are declared and never fire. Because the names belong to core and not to that plugin, another sign-in method (OAuth, magic link) can fire the same points, and a handler need not know which method was used. The magic link plugin does: verifying a link fires `auth.signIn.*`, and `SignInResult.Method` says which plugin it was. The points around requesting a link are the plugin's own (`auth.magicLink.*`); see [`../plugins/magiclink.md`](../plugins/magiclink.md).

Sign-out has no failed point, and no call to `Fail`.

## Design decisions

### A point has one phase

**Context:** A point could carry a list of valid phases (`data.user` with before and after), with handlers registered per point and phase. Chains would then be keyed by both.

**Options considered:**

- *A list of phases per point.* Fewer names to declare. Every lookup needs the pair, the registry and the dispatcher each validate the pair, and a rate-limit rule or an audit spec on the point has to say which phase it means.
- *One phase per point.* More names. A point name alone identifies a chain, a handler type and a contract, so `frozenChains` is keyed by point, an `AuditSpec` belongs to one chain, and a rate-limit rule can be checked against "is this a before point" at declaration.

**Decision:** One phase per point. `HookPointDef.Phase` is a single value and the name carries the moment (`beforeCreate`, `afterCreate`).

**Revisit if:** the number of points per operation grows enough that declaring them one by one becomes a source of mistakes. A helper that declares a group would be the first step, before changing the model.

### In-transaction and committed data points are separate points

**Context:** A data after hook is useful for two different things: writing related rows atomically with the row, and reacting once the row is durable. One point can't promise both.

**Decision:** Two points per write, `afterCreate` and `created`. The reasoning and the options are recorded in [`../models/models.md`](../models/models.md#data-hooks-and-transactions) under "Data hooks run inside the write's transaction" and "After-commit data hooks use an in-memory queue".
